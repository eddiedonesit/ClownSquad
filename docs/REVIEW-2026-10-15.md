# Code review: 2026-10-15

A full sweep of Clown Squad covering architecture, systems, efficiency and
risks. It reflects the code at commit `1f569f3`: 74 C# files, ~18,000 lines,
8 ADRs, 72 commits.

**Overall:**
- **Healthy for a game this far along.** The core ideas hold up well:
  - fighters driven by an input source;
  - moves as data;
  - telegraphs for every attack;
  - atomic saves;
  - assets generated from scripts;
  - a real probe suite.
- **Main risks:**
  - The repository has no backup outside one Drive-synced folder.
  - One very large scene script (`GameRoot`) and global state that crosses scenes are where the next bugs will come from.
  - Online play needs one more abstraction (effects and spawning) before it can start.

## 2. Risks and recommendations

### High

**R1. The project has no backup, and Drive syncs the live repository.**
- **The problem:**
  - `git remote -v` is empty, so all 72 commits exist in one folder.
  - That folder is synced by Google Drive, which copies `.git/` and the `.godot/` cache file by file while Git and Godot are writing them.
  - The 890 MB scratch folder is the sign of it.
  - Drive syncing a live Git repo can leave a corrupt index or a half-written object.
- **Fix (about 15 minutes):**
  - Create a private GitHub (or GitLab) repository and push. That needs your approval because it publishes code to a service.
  - Then either move the project out of the Drive folder, or exclude `.git`, `.godot` and `debug` from sync.
  - Git LFS for `assets/` is worth considering (§R9).

**R2. `GameRoot.cs` is 1,500 lines doing about eight jobs.**
- **What it does:**
  - stage setup, player join, waves, loot and gold;
  - the pause menu;
  - the results screen;
  - the boss rush;
  - about 15 debug and probe flags.
- **Why it matters:** the boss-rush bug (F1) came from two of those jobs meeting. Online play will need to hook player spawning and stage flow, which is hard to do safely in a file this size.
- **Fix:** split it into `StageSession` (setup, flow, rewards), `PauseController`, `ResultsScreen` and `DebugFlags` (all probe and screenshot flags, compiled out of release). This is mechanical, about one session, and the probe suite covers it.

**R3. Global state crosses scene changes.**
- **The settings involved:**
  - `BossRush.Active`, `Campaign.Pending`;
  - `SaveSystem.Path` and `ActiveSlot`;
  - `GameSettings.ForceNormal`, `ArtStyle.Classic`;
  - `Arena.Current`, `WaveDirector.Running`, `Sfx.Instance`.
- **Why it matters:** each one is a setting that one scene leaves behind for the next. F1 was exactly this.
- **Fix:** gather the cross-scene settings into one `Session` record. The title screen creates it, and each mode (campaign, rush, probe) sets it up whole. That makes "what mode am I in?" one question with one answer.

### Medium

**R4. Effects are called directly from gameplay code (353 call sites).**
- **What:** `Sfx.Play`, `ImpactEffect.Spawn`, `PopText.Spawn`, `CameraShake.Request` and `Telegraph.*` are called straight from moves.
- **Why it matters:**
  - Fine offline.
  - Online, every one of them has to reach the clients as well.
- **Fix:** route them through one `Fx` facade now (a mechanical rename). Online then means changing one class instead of 353 call sites. This is the first step of the multiplayer plan below.

**R5. A held sound can be cut off by mistake.**
- **What:** `Sfx` reuses a fixed ring of 24 voices. A move that keeps a voice to stop later (the charge kazoo) can find that voice has meanwhile been reused, so its `Stop()` cuts someone else's sound.
- **Fix:** give looping or held sounds their own voice, or have `Stop()` check the stream.

**R6. Input is hard-coded in four places.**
- **The four:** `LocalDeviceInput`, `MenuPad` (in StatTent.cs), `MapPad` and `PauseMenu.PauseHeld` each read keys and buttons directly.
- **Why it matters:** there is no rebinding, which Steam players expect and accessibility needs.
- **Fix:** move to Godot `InputMap` actions per device, plus a rebinding page in Settings, which also merges the two menu-pad classes.

**R7. Debug and probe code ships in release builds.**
- **What:**
  - Command-line flags such as `bossrush`, `fight bossnow`, `wavetest` and `level 30` work in any build.
  - The probe save path is chosen in gameplay code.
- **Fix:**
  - Gate them on `OS.IsDebugBuild()`.
  - Move them into `DebugFlags` (R2).

**R8. Leak warnings at exit.**
- **What:** "N ObjectDB instances leaked / resources still in use". These come from static caches (Kit3D meshes, FrameLibrary, Portraits, LitSprite, `EnemyShot.GlassPaint`).
- **Why it matters:** harmless today, but it hides any real leak in the noise.
- **Fix:** add a `Caches.ClearAll()` on quit, so the report goes quiet and any later warning means something.

**R9. Audio size.**
- **What:** 245 MB of WAV (about 12 songs of ~20 MB each).
- **Fix:**
  - Convert the music to Ogg Vorbis, roughly 10× smaller and streamed. That cuts the Steam download and repo size a lot.
  - Sound effects can stay WAV.
  - This needs a small change to the loop-point code (`music_loops.json` → `AudioStreamOggVorbis.loop_offset`).

**R10. Weapon perks are recomputed on every call.**
- **What:** `Weapons.Perks(record)` is recomputed whenever `MaxHealth`, `CritChance` or `LootBoost` are read, and `Weapons.Learned` adds an empty list when it is only *read*.
- **Why it matters:** cheap today. But it is a hidden write on a read path, which surprises the next person to change it.
- **Fix:** keep a perks cache keyed on the record's skill version.

**R11. Balance needs human hands.**
- **What:**
  - The smart bot wins 7-B (Pyro Pete) about half the time.
  - It reaches boss 7 of 10 in the boss rush.
  - All 8 weapons beat 3-B at level 12.
- **Fix:** the bot is a regression tool, not a balance oracle. Playtest weapons and the late bosses next.

### Low

- **R12.** `Portraits.FaceOf` and `SkillMenu.WeaponFrame` scan sprite pixels with `GetPixel` on first use, which causes a small hitch the first time a menu opens. They could be computed by the Python generator and stored in `frames.json`.
- **R13.** All text is English string literals. Localisation (for Steam reach) wants a string table; cheap to start now, expensive later.
- **R14.** Move numbers (damage, timings, cooldowns) live in C#. A JSON tuning table would let balance changes skip a rebuild. Worth it once playtesting starts in earnest.
- **R15.** `.tmp.driveupload/` is also scanned by the Godot editor on start-up (4,574 files). It goes away with R1.

## 3. Architecture notes: what is working

- **Input sources (ADR 0003).**
  - Players, AI, the smart test bot and the probes all drive fighters through `IInputSource`.
  - That is exactly the hook remote players need.
- **Moves as data.** `AddMove(name, range, cooldown, start, tick, weight)` keeps 6 enemies and 9 bosses readable.
- **Telegraphs as data.** `Telegraph.Covers` lets the bot, and later the AI or a replay checker, reason about danger.
- **Saves.**
  - Atomic write (temp file then replace), versioned (now v5).
  - An unreadable file is set aside, never overwritten.
- **Generated assets.** Every sprite, sound and song is rebuilt from `tools/`, so art changes are diffs to code.
- **Probes.** `wavetest`, `losetest`, `movetest`, `weapontest` and the smart bot, now one command (F9).

## 4. Online multiplayer: status and plan

**Status: not started. Zero networking code exists.** The groundwork is in place:

| Ready | Not ready |
|---|---|
| Fighters take input only through `IInputSource`, so a remote player is one new class | Effects (353 call sites) and spawned objects are created directly, with no replication hook (R4) |
| Host-authoritative design is decided (ADR 0003); all loot, spawn and shop rolls happen in one place, and encounters are seeded | `GameRoot` mixes flow and presentation (R2), so a client "puppet" mode has nowhere clean to live |
| Local co-op works (up to 4 on one machine), so multi-player flow, shared camera and per-player records are exercised | Menus (map, shop, inventory, skills) assume every player is on this machine |
| Single-player is just co-op with one player | Character records live in the host's save; a guest's clown must come from the guest's own save |

**Recommended approach: host-authoritative "puppets", Godot high-level multiplayer over ENet, direct IP, no matchmaking.**
- The host runs the whole game exactly as today.
- Clients do no simulation. They send their `InputCommand` every frame and draw what the host tells them.
- This is the brawler-standard approach. It avoids lockstep's desync risk (rejected in ADR 0003) and needs no prediction to start, at the cost of the guest feeling about one round trip of input lag.

### Phases

| Phase | What | Size |
|---|---|---|
| **0. Prep** (offline, safe now) | R4 `Fx` facade; R2 `StageSession`; give every spawned thing (fighter, shot, telegraph, hazard, pickup) a `NetId` from one registry | 1–2 sessions |
| **1. Connect** | Title → ONLINE → HOST (port 7777) or JOIN (type an IP). Lobby shows who is in, each picks a clown; the guest sends their character record (level, stats, gear, weapon, skills) from their own save | 1 session |
| **2. Play a stage** | `RemoteInput : IInputSource` on the host, fed by an unreliable-ordered RPC from each client's `LocalDeviceInput`. Host broadcasts a snapshot 20–30 times a second (each NetId: position, facing, clip/frame, health, tint) plus reliable events (spawn/despawn, effects via `Fx`, sounds, camera, wave and HUD state). Clients interpolate between snapshots | 2–3 sessions |
| **3. Campaign flow** | Host drives the map and stage choice; results, XP, gold and loot are sent to each guest, who saves into their own file. Shops, inventory and skills run locally on each machine and send the changed record back | 1–2 sessions |
| **4. Polish** | Disconnect handling (a guest drops: their clown leaves; host drops: session ends, guests' progress so far is saved), a ping display, a latency option for testing, optional client-side prediction for the guest's own movement | 1–2 sessions |

**What to know before starting:**
- **Internet play over direct IP needs the host to forward a UDP port.**
  - LAN and VPN tools (Tailscale, ZeroTier, Radmin) work without that, which is fine for testing with friends.
  - For release, Steam Networking (GodotSteam: friends' invites, no port forwarding) slots in as a different transport under the same RPCs. The ADR already planned for Steam P2P.
- **Testing** can be two copies of the game on one PC (host and `127.0.0.1`), and the smart bot can play the guest for automated probes.

**Recommendation:** do Phase 0 next. It is worth doing for its own sake (R2, R3, R4) and is safe to do while weapons are being playtested. Phases 1–2 then give a playable online stage.

## 5. Suggested additions

Ordered roughly by value for effort.

1. **Weapon pickups in the field.** A weapon rack in bonus stages, or a rare drop, lets players try a weapon for one stage without changing their loadout. Good for discovery now that there are eight.
2. **Team-up moves for co-op.** Two players attacking the same launched enemy trigger a shared finisher (a "seesaw launch", a "pie relay"). This is the genre's best co-op hook, and the data is already there (`Launched`, `LastAttacker`).
3. **Daily circus.** A seeded daily stage with modifiers (all enemies Rare, pies only, low gravity) and a local best score. It is cheap because stages are already seeded.
4. **Practice ring.** The old sandbox, made a menu option, lets players try every weapon and charge move on dummies, which shows off the eight weapons.
5. **Controller rebinding and accessibility** (R6): rebinding, colour-blind-safe telegraph colours, screen-shake already done, "hold to charge" as a toggle.
6. **Steam essentials:** achievements (first win per weapon, each boss, the boss rush under a target time), Steam Cloud for the save slots, rich presence.
7. **Boss rush and daily leaderboards** (Steam leaderboards) once Steam is wired.
8. **Photo mode and replay of the last boss kill**, using the slow-motion final blow that already exists. Shareable clips sell games.
9. **More enemy variety per world:** each world's new enemy gets an "elite" late-game variant with one extra move (a juggler who juggles bombs, a mime who builds a box around you).
10. **Accessibility difficulty option:** a separate assist toggle (more i-frames, slower telegraphs) independent of Easy/Normal/Hard.
